# pult-kachestva-tests

Автотесты JSON API «Пульта качества» — отдельный репозиторий, отдельно от кода
продукта ([pult-kachestva](https://github.com/Snazzykk/pult-kachestva)). Обычная
для компаний схема: у разработчиков — свой репозиторий, у тестировщиков — свой,
со своей историей изменений и своим CI.

У «Пульта качества» нет постоянно задеплоенного стенда (это локальный инструмент) —
поэтому вместо похода по `preprod`/`prod` URL тесты сами поднимают
`python run.py` из репозитория `pult-kachestva` на время прогона, на отдельном
порту и scratch-файле состояния, и гасят его в конце. Реальные данные пользователя
(`data/quality-state.yml`) тесты никогда не трогают.

## Устройство (по образцу типового test-репозитория)

```
configuration.py     стенд: адрес/порт (STAND) + путь к репозиторию pult-kachestva
endpoints/
  pult_endpoints.py   сырые пути ручек API
helpers/
  api_helper.py        ApiClient — requests.Session + логирование запроса/ответа в Allure
  pult_helper.py        PultAPI — фасад с именованными методами над endpoint's
  allure_helper/
    allure_assertion.py  assert_status_code/assert_equals/... — каждая проверка
                            сама оборачивается в allure.step и прикладывает
                            ожидаемое/фактическое значение, не голый assert
conftest.py           фикстуры: поднять/погасить сервер, api, clean_state
tests/
  test_state_api.py     /api/state, /api/yaml, /api/meta
  test_security.py      CSRF (Origin vs Host)
  test_openapi_import.py  /api/openapi
  test_tms_import.py      /api/tms
# каждый тест: @allure.title("человеко-читаемое название") + тело
# разбито на именованные with allure.step(...) — в отчёте видна не
# только пройденная/упавшая точка, а весь ход теста
scripts/
  send_telegram_notification.py   итоги прогона в Telegram (см. ниже, опционально)
```

## Запуск локально

Ожидается стандартный layout — `pult-kachestva` склонирован рядом, соседним
каталогом:

```
Users/you/pult-kachestva/
Users/you/pult-kachestva-tests/
```

```bash
python -m pip install -r requirements.txt
python -m pytest                 # весь набор
python -m pytest -m smoke        # только быстрый набор
python -m pytest -m regress      # набор для master (включает всё)
```

Если `pult-kachestva` лежит не рядом — укажи путь явно:

```bash
PULT_REPO_PATH=/путь/к/pult-kachestva python -m pytest
```

Полезные переменные окружения: `PULT_TEST_HOST` / `PULT_TEST_PORT` (по умолчанию
`127.0.0.1:7997`) — на каком порту поднимать сервер на время тестов.

**Параллельный запуск (`pytest-xdist -n auto`) сознательно не используется** —
каждый воркер поднимал бы свой собственный сервер отдельным процессом, и под
нагрузкой это давало нестабильные `ConnectionError`. Набор маленький (~1.5 секунды
последовательно) — выигрыш от параллели не окупает нестабильность.

## CI (GitHub Actions)

`.github/workflows/api-tests.yml`. Прямой связи с репозиторием `pult-kachestva`
нет (мердж туда не триггерит тесты здесь автоматически) — запуск:

- **вручную** — вкладка Actions → «Pult API tests» → Run workflow. Можно указать
  ветку/тег `pult-kachestva` для проверки (`pult_ref`, по умолчанию `master`) и
  фильтр по маркеру (`markers`: `smoke` / `regress`, пусто — весь набор);
- **по расписанию** — раз в сутки, полный набор на `master`.

Что делает workflow: чекаутит себя и `pult-kachestva` (в подкаталог), ставит
зависимости, гоняет `pytest` (с ретраями на упавших), собирает Allure-отчёт и
публикует его на GitHub Pages (`https://<user>.github.io/pult-kachestva-tests/`),
кладёт сырые результаты артефактом, и — если заданы секреты — шлёт итог в Telegram.

**Разовая настройка репозитория на GitHub** (руками, не через git push):
Settings → Pages → Source → **GitHub Actions** (иначе `actions/deploy-pages`
падает — Pages должен быть явно переключён на этот режим).

**Уведомление в Telegram — опционально.** Ничего не отправится, пока не заданы
секреты репозитория (Settings → Secrets and variables → Actions):

- `TELEGRAM_BOT_TOKEN` — токен бота (получить у [@BotFather](https://t.me/BotFather));
- `TELEGRAM_CHAT_ID` — куда слать (свой user id или id чата/канала).

Без них шаг отправки просто печатает в лог «секреты не заданы» и завершается
без ошибки — на прохождение тестов и остальной пайплайн не влияет.

## Пилот AI-review через API

Подключён локальный launcher `scripts/ai_review.py` и отдельный ручной workflow
`.github/workflows/ai-review.yml`. Движок `ai-reviewer 0.17.1` берётся из приватного
`Snazzykk/AI-CICD`, commit `07ea5f46644fe176e3b17945f150ef9fcc9a704c`, каталог
`ai-review-study/aireviewer`. Его исходники в этот публичный репозиторий не копируются.

Пилот проверяет diff между общей базой веток и выбранным head commit. Он оставляет
основное ревью, общий обзор и перепроверку замечаний; все три используют одну модель.
Результат — Markdown-отчёт, JSON замечаний и usage. Ручной workflow не является
проверкой, блокирующей merge. После успешного полного прогона workflow публикует
итоговый review и замечания к строкам в GitHub PR через отдельный адаптер.
Если PR успел измениться или закрыться, публикация останавливается, а отчёт остаётся
в Actions. Неполные прогоны не публикуются как готовое ревью.

Текущий провайдер — Polza: `AI_REVIEW_BASE_URL=https://polza.ai/api/v1`.
Модель — `qwen/qwen3-coder-30b-a3b-instruct@provider=siliconflow/fp8&allow_fallbacks=false`:
закреплён провайдер и отключён fallback. Переменная `OPENAI_API_KEY` содержит ключ
Polza — это имя настройки совместимого клиента. В GitHub включён экономный режим;
автоматических запусков при push, PR или по расписанию нет.

### Локальный запуск

Нужны Git, Python 3.12+ и доступ к API, поддерживающему Chat Completions:
`temperature`, `max_tokens`, `response_format=json_object`. Некоторые reasoning-модели
не принимают эти параметры. Совместимость выбранной модели проверяется реальным запуском.

Установите движок в отдельное окружение, указав путь к своему клону AI-CICD:

```powershell
python -m venv .venv-review
.\.venv-review\Scripts\python.exe -m pip install --index-url https://pypi.org/simple '<AI-CICD>/ai-review-study/aireviewer'
```

Перед установкой проверьте `git -C '<AI-CICD>' rev-parse HEAD`: нужен commit,
указанный выше. Обычный `uv sync` здесь не подходит: snapshot содержит placeholder
корпоративного индекса пакетов. Зависимости приложения и его тесты устанавливать
для ревью не требуется.

Задайте адрес API (обычно заканчивается `/v1`) и точное имя доступной модели:

```powershell
$env:AI_REVIEW_BASE_URL = 'https://<адрес-провайдера>/v1'
$env:AI_REVIEW_MODEL = '<имя-модели>'
.\.venv-review\Scripts\python.exe scripts/ai_review.py --base HEAD~1 --head HEAD --check
.\.venv-review\Scripts\python.exe scripts/ai_review.py --base HEAD~1 --head HEAD --economy --prompt-key
```

`--check` работает без обращения к модели и показывает, что подготовлено.
`--prompt-key` запрашивает API-ключ скрытым вводом, если `OPENAI_API_KEY` ещё не задан.
Ключ не нужно записывать в команду, файлы репозитория или чат. Результаты каждого
запуска сохраняются в новом подкаталоге `ai-review-results/`.

Перед запуском head должен быть текущим `HEAD`, а отслеживаемые файлы — чистыми.
Для PR переключитесь на его ветку и используйте `--base origin/master --head HEAD`.
Если проверяемая ветка содержит собственные изменения launcher, запускайте доверенный
launcher из отдельной копии с `--repository-root <путь-к-ветке>`.

По умолчанию заложено окно контекста 32768 токенов, максимум 8192 выходных токенов
на основной запрос и 16384 на общий обзор. Reasoning-модель тратит часть этого
лимита на рассуждение; слишком маленький лимит может оставить ответ без JSON.
`--context-tokens` должен соответствовать выбранной модели. Это ограничения
запроса, а не денежный лимит прогона; лимит расходов задаётся у провайдера API.
Внешние MCP-проверки, личные и проектные skills, проектные rules/context, сохранение
промптов и публикация отключены для воспроизводимого первого пилота. Используются
встроенные правила движка. При запуске сохраняются отдельные артефакты движка;
не публикуйте весь каталог результатов без просмотра.

`--economy` ограничивает ответы 2048 токенами, общий обзор — 4096, diff — 5 файлами
и 300 строками. Judge читает окна по 20 строк вместо целых файлов; размер пакета —
12000 символов. Повторы API отключены. Это ограничение объёма работы, не фиксированный
денежный лимит: стоимость зависит от модели и текущего тарифа.

### Ручной запуск в GitHub

После попадания workflow в default branch (`master`) добавьте в
Settings → Secrets and variables → Actions:

| Тип | Имя | Значение |
|---|---|---|
| Secret | `OPENAI_API_KEY` | Ключ выбранного API |
| Secret | `AI_REVIEW_SOURCE_SSH_KEY` | SSH deploy key с доступом только на чтение `AI-CICD` |
| Variable | `AI_REVIEW_BASE_URL` | HTTPS endpoint Chat Completions без `/chat/completions` |
| Variable | `AI_REVIEW_MODEL` | Доступная модель |
| Variable, необязательная | `AI_REVIEW_CONTEXT_TOKENS` | Размер окна; по умолчанию 32768 |

Откройте PR из ветки этого репозитория, затем Actions → **AI review (manual pilot)** →
Run workflow, branch `master`, номер PR. Первый пилот не принимает PR из forks.
Workflow использует launcher из доверенного commit default branch, а код PR только
читает; установка пакетов и выполнение тестов из PR не выполняются.
Отчёт находится в Summary запуска и артефакте `ai-review-pr-…`, срок хранения — 3 дня.
Без настроенных секретов запуск завершится ошибкой до обращения к модели.
Launcher также проверяет метрики полноты ревью: сбой запросов, потерянный JSON,
обрезанный ответ или неперепроверенные замечания приводят к ошибке запуска,
даже если исходный движок сохранил отчёт и завершился с кодом 0.

Для оценки качества используйте отдельный PR с двумя заранее известными дефектами
и одной корректной правкой. Сравните замечания с ожидаемыми, проверьте номера строк,
ложные срабатывания, usage и повторный ручной запуск. Тестовый API-ответ проверяет
только интеграцию; качество модели и публикацию в рабочем GitLab проверяют отдельно.

### Результат первого локального пилота, 9–10 ноября 2026

В отдельной копии проекта внесены два подтверждённых дефекта: порт клиента смещён
на +1 и все HTTP-методы заменены на GET. Третья правка меняет только docstring.
Во всех трёх попытках итоговый отчёт указал оба дефекта на правильных строках
(19 и 29) и не добавил замечаний к docstring. Это маленький учебный пример,
он не измеряет качество ревью реальных задач.

Полностью успешных прогонов по строгой проверке — 0 из 3: первый оставил два
замечания без вердикта judge; второй потерял общий обзор после пустого ответа API;
третий завершил обзор и judge, но содержал один повреждённый элемент JSON основного
ревью. Первые два прогона использовали лимит ответа 4096, третий — текущие лимиты
8192/16384. Исходный движок считал эти прогоны успешными; launcher теперь возвращает
ошибку и сохраняет диагностику. Учёт OpenRouter после пилота показал usage 0.

Проверки launcher: 19/19 unittest; новый workflow прошёл actionlint 1.7.12.
На этой бесплатной модели надёжность полного процесса пока не подтверждена.
Для рабочего использования нужны проверка другой модели/API и отдельная проверка
публикации в GitLab. Результаты локального эксперимента сохранены вне репозитория,
в `Work/research/ai-review-pilot-2026-11-09/`.

### Проверка Polza, 10 ноября 2026

Один прогон Qwen3 Coder 30B в экономном режиме технически завершил все этапы.
Основное ревью нашло оба учебных дефекта, однако judge ошибочно отклонил оба,
оставив итоговый отчёт без замечаний. Технический успех не подтверждает качество
ревью: эта модель на данном примере пропускает реальные ошибки после перепроверки.
Расход по разнице баланса — 0,12155394 ₽, остаток — 42,09432936 ₽.
Launcher проверен 21 unittest; workflow — actionlint. Качество модели для рабочего
использования пока не подтверждено; дополнительные платные прогоны не запускались.
